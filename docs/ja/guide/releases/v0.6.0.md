# NyankoFace v0.6.0

NyankoFace v0.6.0では、表示中のplatformを測りやすくし、次のoperator判断を
説明しやすくしました。repositoryのview、完了したdownload、activeなlikeを
1つのPostgreSQL event ledgerと範囲制限付き時系列APIで扱います。同時に、
navigation選択後のclose、tabletでwrapするSpace header、MCP setupの
repository contractも整えました。

## Highlights

- **1つのledgerから実測activity:** `nyankoface_metrics.metric_events`を、
  browser／agentのsuccessful view、完了したRaw／LFS／Automation download、
  activeなagent likeのcanonical sourceにしました。累計cardとday／week／month
  seriesは同じevent集合を使い、`data`、`no_data`、`unavailable`を区別します。
- **clickではなく完了を数えるdownload:** frontend proxyのresponse bodyが完了した
  場合だけeventを記録します。Raw、LFS、Automationを区別し、operation keyで
  retryを冪等にします。failed、denied、cancelled、bot、health-checkは実測totalを
  増やしません。
- **静かなresponsive surface:** navigation menuは選択後に閉じ、監査したsurfaceで
  NyankoFace brandを揃え、tabletでheaderがwrapしてもSpace identity、tab、metric、
  runtime controlを使えるようにしました。
- **検証しやすいMCP setup:** client READMEとexampleで、Streamable HTTP、local
  stdio互換、file-backed credential、安全なconfig validation、security boundaryを
  明記しました。
- **logo方向をevidenceとして保存:** 10候補とvariant matrixを[Issue #177 evidence](../../../evidence/issues/177/README.md)
  に保存しました。方向が決まる前にproduction logoを暗黙に置き換えず、探索をreview可能にしています。

## Operator impact

- v0.6.0のrunner startupは、既存の`nyankoface_metrics` database内に
  `metric_events` tableとindexを作ります。既存のviewとactive-like counterは
  安定したlegacy idempotency keyでbackfillされます。自動・冪等・非破壊のため、
  metrics専用の手動migration commandは不要です。
- upgrade前に`nyankoface_metrics`をbackupし、dumpとrestore evidenceを保持します。
  ledgerは自動pruneされません。3つのPostgreSQL databaseとnamed volumeの保護は、
  [upgradeとデータ保持のrunbook](../upgrading)の契約を続けてください。
- このreleaseで必須の新しいenvironment variable、database、named volumeはありません。
  既存のMCP環境ではfile-backed tokenとstateのbackup契約を守ってください。

## Validation

release candidateでは、Compose validation、frontendのtype／test／build、bilingual docs integrityと
VitePress build、PythonとSkill validation、PostgreSQLを使うSpaces runner test、maintenance-agent test、
SVG asset validation、release QA inventory validatorを実行します。final releaseでは登録済みCIの成功、
live docs URL、公開GitHub releaseの検証も必要です。

手動runtime captureはCI gateではなくevidenceです。production rollout前にpublic repository、
Raw／LFS／Automation download、activity series、responsive Space header、navigation close、
MCP client configurationを実際に確認してください。

## Upgrade contract

- **Target path:** `v0.5.0`から`v0.6.0`、またはfresh install。さらに前のreleaseは途中のrelease noteを先に確認します。
- **Breaking change:** 必須のCompose、environment variable、image、volume contractは意図的に変更していません。
  UIには実測stateが加わり、runnerは既存counterの隣に互換性のあるledgerを追加します。
- **Migration:** metrics初期化は自動かつ冪等です。`metric_events`とindexを作り、既存counterを安定keyでbackfillします。
  欠落historyを推測せず、eventを自動pruneもしません。v0.4.0 SQLite pipeline migrationはv0.5.0のupgrade pathです。
- **Backup:** `forgejo`、`nyankoface_metrics`、`nyankoface_maintenance`をdumpし、必要なnamed volume、MCP state、
  credential sourceをarchiveします。比較が終わるまでold checkout、dump、archive、redacted manifestを保持します。
- **Rollback:** health、schema initialization、data comparisonが失敗したら対象serviceを停止し、logとbackupを保持します。
  reviewedなv0.5.0 checkout／imageと検証済みPostgreSQL／volume backupへrestoreし、named volumeを削除したり
  metrics ledgerをin-place downgradeしたりしません。
- **更新後:** ComposeとPostgreSQL health、repositoryとSpace access、view／download／like total、時系列bucket、
  agent identity、pipeline state、maintenance history、runtime log、navigation、tablet layoutを比較します。
  比較がない項目はpassではありません。
- **既知の条件:** 完了したdownloadがgraphへ反映されるのは次のrequestになる場合があります。public series windowは
  366日までで、空期間は`no_data`、service unavailableは`unavailable`です。logo候補は別途方向を選ぶまで探索状態です。

live deploymentを変更する前に、完全な[upgradeとデータ保持のrunbook](../upgrading)を実行してください。
